类案检索 API：语义向量 vs 关键词，到底哪种更准？（2026 法律 AI 工程实战）

做类案检索的团队几乎都在同一个路口纠结：到底用关键词（BM25）还是语义向量（embedding）？本文从法律文本的特殊性讲到生产级混合检索 + 重排 + 回链的完整架构，以及评测指标与自建/接 API 的取舍。

类案检索 · 语义检索 · 关键词检索 · API

做类案检索的团队，几乎都在同一个路口纠结过：到底是用关键词（BM25）还是语义向量（embedding）？

有人发现纯关键词漏掉了换个说法的类案，转头全押向量；又发现向量把"看起来很像、其实判得完全相反"的案子也召回了，信心崩塌。两边都踩过坑之后才明白：这道题的正确答案不是二选一，而是理解法律文本到底"特殊"在哪里。

一、先说结论：这不是二选一

关键词和向量不是竞争关系，是互补关系。生产里真正能用的类案检索，是把两路召回融合、再加一层重排把结果排对——而最后，无论用什么算法，每条结果都得能点回原文核对。

二、法律文本特殊在哪：三条决定一切的特性

不理解这三点，选型就是在拍脑袋：

  1. 关键差异常常藏在"数字和法条号"里——两份判决正文九成相似，差别只在"判二倍赔偿"还是"判经济补偿"、是否适用某条司法解释。对通用向量模型来说，这点差异在几百维空间里可能几乎被抹平。语义相似 ≠ 裁判后果相似。
  2. 术语高度专属，差之毫厘谬以千里——"违法解除"和"经济性裁员"、"定金"和"订金"，在通用语料里可能被压得很近，但裁判结果完全不同。法律检索需要的是领域适配的表示。
  3. 案由是结构，不是一句话——案由是一套有层级的 taxonomy 体系，本质是结构化标签。最强的过滤信号往往来自结构字段（案由 + 审级 + 法院层级 + 时间），而不是把整段文本丢进向量里硬算。

三、关键词检索（BM25）：什么时候是它最强

场景 关键词表现
按案号 / 法条号查 ✅ 精确命中，不可替代
专有术语、当事人名、机构名 ✅ 准，且可解释
必须包含某个法定要素 ✅ 可强约束
换了说法的同义类案 ❌ 漏召
只描述情节、没用法言法语 ❌ 召回差

一句话：关键词在"精确"和"可解释"上无可替代，但它召不回换了说法的类案。

四、语义向量检索（embedding）：它补什么、又会怎么翻车

向量检索补的正是关键词的盲区：

  • 同义 / 近义召回："被公司变相逼走"能召回到"未协商一致调岗降薪"等法律表述的类案
  • 口语 → 判决用词的跨越：用户写"老板拖着不发工资还把我开了"，能召回拖欠劳动报酬 + 违法解除的判决
  • 情节相似但措辞不同：把争议焦点相近的案子拉到一起

但纯向量会在三个地方翻车，且都很隐蔽：

  1. 精确点失准——案号、法条号、金额这类需要精确匹配的，向量会"近似"而非命中
  2. 伪类案——正文九成像、关键裁判后果相反的判决被排到前面（最危险）
  3. 通用模型术语压缩——违法解除 vs 经济性裁员被通用 embedding 拉近，召回不分

工程提醒：别直接拿通用 embedding 模型上法律类案检索。要么用法律领域语料适配过的表示，要么至少叠加结构化字段过滤（先用案由/审级/时间把候选集圈对）再算语义相似度。

五、生产级答案：混合检索 + 重排 + 回链

成熟的类案检索 API 通常是这样一条流水线：

  1. 结构化预过滤：先用案由、审级、法院层级、时间范围把搜索空间圈到对的子集
  2. 两路并行召回：关键词（BM25）保精确与可解释，向量保同义与情节相似，各取 top-N
  3. 融合 + 重排（rerank）：用 cross-encoder 对"查询—判决"对逐一打分，把真正相关的排上去、把伪类案压下去
  4. 回链原文：每条结果带案号 + 可点开的原文链接

关键不是某个参数，而是这条链路的设计：结构过滤定边界、双路召回保全面、重排保精度、回链保可信。四者缺一，生产里都会出问题。

六、评测：别只看"召回了多少"，要看"前几条对不对"

  • Recall@K：真正的类案有没有进到前 K 条候选
  • nDCG@10 / MRR：相关的有没有排在前面（律师只看前几条）
  • 伪类案率：前排里"看着像、判得反"的比例——法律检索特有、最该盯的反向指标

建一个小而真实的评测集（让懂业务的人标几十个查询的"正确类案"），每次改算法都跑一遍。没有评测集的调优都是自我安慰。

七、自建还是接 API：看你卡在数据还是算法

混合检索 + 重排这套算法本身，有经验的团队两三周能搭起来。真正的瓶颈几乎总在数据底座：

  • 自建（裸爬数据）：覆盖不可表征、字段要自己抽、去重易污染、回链不稳定、上手以月起
  • 接类案检索 API：全量 1.6 亿+ 可表征、字段已结构化、已去重归并、稳定回链、试用 key 当天接通

数据不出域怎么办？ 对律所、法院、检察院、政府，涉密数据不能出内网时，正确路径是先用 API 验证检索质量，再上私有化离线部署——全量裁判文书 + 检索引擎 + 模型都跑在内网。

八、常见问题

Q：只用向量检索行不行？ 不建议。你会在案号/法条号精确查询和"伪类案"上持续翻车，而这两类恰恰是法律场景的高频与高危。

Q：重排模型一定要吗？ 强烈建议。双路召回保证"该有的都在候选里"，但排序往往不对；重排是把相关的排上来、伪类案压下去最有效的一步。

Q：用大模型直接做检索不就行了？ 大模型负责理解查询和归纳结果，但不该负责"记住判例"——那正是它会编案号的根源。正确分工是：检索系统找真实判决并回链，大模型在检索到的真实内容上作答。
